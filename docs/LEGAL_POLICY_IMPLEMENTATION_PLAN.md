- 응시 경로에서 푸터를 숨기는 기존 동작은 유지한다.

## 5. 결제 화면과 동의 기록

결제 버튼 바로 위에 아래 원문을 배치한다. 원본의 `[필수]` 표기는 대괄호 마스킹 대상이며, 체크박스에는 필수 상태를 별도로 전달한다.

> 디지털 자료는 결제 즉시 제공되며, 내려받기 또는 열람을 시작하면 청약철회(단순 변심 환불)가 제한됩니다. 다만 자료가 설명과 다르거나 파일 오류가 있으면 환불받을 수 있습니다. (환불정책 보기)

체크박스 문구: **위 내용을 확인했으며 즉시 제공에 동의합니다.**

기존 금액 확인 체크박스와 합치지 않고, 기본값은 미동의로 둔다. 아래에 이용약관·개인정보처리방침·환불정책 링크를 둔다.

현재 주문에는 동의 시각 필드가 없고, `payment-start`는 허용하지 않은 요청 필드를 거부한다. 결제 이벤트 테이블도 결제·실패·취소·환불 용도다. 따라서 기존 요청에 필드를 끼워 넣거나 결제 이벤트를 다른 용도로 쓰지 않는다.

| 순서 | 동작 | 실패·재시도 |
|---|---|---|
| 1 | 기존 `payment-start`가 주문과 서버 기준 가격을 준비 | 기존 계약 유지 |
| 2 | 사용자가 금액 확인과 별도의 환불 고지 동의에 체크 | 둘 중 하나라도 미동의면 결제 SDK를 호출하지 않음 |
| 3 | 새 `order-consent` API가 인증·주문 소유권·동의 대상·버전을 확인 | 서버에서 검증 실패하면 기록하지 않음 |
| 4 | 별도 `order_policy_consents`에 주문 ID·사용자 연결·동의 종류·버전·고지 해시·서버 시각 기록 | 브라우저 시각을 증거로 쓰지 않음. 같은 주문·버전 중복 요청은 동일 기록으로 처리 |
| 5 | 저장 완료 응답의 주문·버전을 확인한 뒤 기존 결제 SDK 호출 | 기록 저장 실패 시 결제를 시작하지 않고 재시도 제공 |

견적·상품 또는 고지 버전이 바뀌면 해당 동의를 초기화한다. 금액·SKU·결제 상태·권한·다운로드 상태는 동의 API가 변경하지 않는다. IP 주소·기기 정보 등 추가 정보는 수집하지 않는다.

테이블은 RLS를 활성화하고 브라우저의 직접 쓰기 권한을 차단한다. 서버 API에서 인증과 소유권을 검증한 후 제한된 기록만 추가한다. [Supabase RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)를 기준으로 권한 허용·거부 검증을 포함한다.

**보장 범위:** 정상 웹 결제 흐름은 동의 저장 완료 후 진행된다. 기존 결제 서버 계약을 그대로 두므로, UI를 우회한 외부 결제 요청까지 동의 기록을 필수로 강제하지는 않는다. 모든 결제의 서버 강제가 필요하면 기존 결제 진입점에 검사를 추가해야 하므로 별도 계약 변경으로 제안한다.

**운영 적용 전제:** 새 테이블/API가 운영에 적용되기 전에는 운영 동의 저장을 검증했다고 주장하지 않는다. 이번 작업은 로컬 구현·검증까지만 수행한다. 기록 보유·삭제 기준은 확정된 개인정보 운영 정책과 함께 확인하며 임의 기간을 정하지 않는다.

| `supabase/migrations/<CLI가 생성한 이름>_order_policy_consents.sql` | 주문 연결 동의 테이블·권한·중복 방지. 기존 결제 테이블 변경 없음 |
| `scripts/validate-legal-content.mjs` 및 필요한 API 테스트 | 원문 보존·마스킹·유효 링크·동의 보안과 실패 경로 검사 |
| `docs/STORE_MOBILE_QA.md`, `docs/PAYMENT_CONTRACT.md` | 변경 전후 QA 및 별도 동의 API의 경계 기록 |

파일명은 위 구성을 기준으로 하되 기존 컴포넌트 재사용 여부에 따라 중복을 줄인다. 기존 작업 중인 파일의 수정은 보존하고 이번 변경분만 구분해 기록한다.

DB/API 검증은 로컬 환경에서 수행한다. 사용 가능한 로컬 환경이 없으면 정적·모의 검증과 실제 DB 검증 미실시를 구분해 보고한다. 실제 결제나 운영 DB 접근으로 이를 대신하지 않는다.

정책 페이지는 신규이므로 변경 전에는 경로 부재를 기록하고, 푸터·결제·시험 메뉴는 동일 화면의 전후를 비교한다. PC 검증은 768px 및 1280px를 포함한다. 미래 탭 높이를 임시 테스트 값으로 넣어 푸터 가림을 검사한 뒤 원래 기본값 0으로 되돌린다.

## 8. 변경 묶음과 롤백

승인 후 아래 단위로 변경을 분리한다. 아래는 예정 커밋 이름이며 아직 커밋하지 않았다.

| 순서 | 예정 커밋 | 포함 범위 | 되돌리기 |
|---|---|---|---|
| A | `feat: add policy pages and legal footer` | 설정·본문·정책 페이지·푸터·시험 메뉴 | A만 되돌리면 해당 UI와 경로 복원 |
| B | `feat: add isolated order consent records` | 신규 로컬 마이그레이션·동의 API·권한 검사 | 운영 미적용 상태에서는 소스 변경 되돌림. 기록된 운영 데이터 삭제는 별도 판단 |
| C | `feat: require refund consent before checkout` | 결제 고지·체크박스·동의 저장 후 기존 SDK 호출 | 먼저 C를 되돌려 신규 API 의존 해제 |
| D | `docs: record policy and consent verification` | QA·캡처 위치·계약 경계·검사 결과 | 필요할 때만 문서 변경 되돌림 |

전체 롤백은 의존 순서대로 C → B → A를 되돌린다. 이전 모바일 최적화 등 기존 변경을 포함한 전체 체크아웃 초기화는 하지 않는다. 만약 이후 운영에 동의 기록이 생겼다면 테이블을 삭제하거나 기록을 지우는 롤백은 자동 실행하지 않는다.

## 9. 승인 시 확인할 사항

1. **정책 페이지·푸터·시험 메뉴·결제 고지와 별도 동의 기록 테이블/API를 로컬에서 구현하는 계획**을 승인하면 적용을 시작한다. 운영 배포·운영 DB 변경은 포함하지 않는다.
2. 환불 선택 조항, 개인정보 본문의 작성 안내, 불완전한 문장, 오탈자는 이 승인으로 고치지 않는다. 삭제·교정을 원하면 해당 문구에 대한 별도 결정을 받는다.
3. 문의 링크는 실제 이메일/URL 확인 전까지 생략한다. 나머지 미확정 사업자 정보도 빈 줄 없이 생략한다.

현재 이 문서만 작성했다. 구현·마이그레이션·빌드 검증 결과는 승인 후 실제 수행 결과로 추가한다.
