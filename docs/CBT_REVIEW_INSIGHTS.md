Wrong-answer and result-page explanation behavior stays available.

Result details and the wrong-note dialog share the same editor (2,000 characters, explicit save). The editor starts collapsed and opens on demand; the action uses an SVG chevron with fixed dimensions. Saving before answering neither grades nor locks the question and does not mark it reviewed. Reuse `wrongNotes.memo`, the local browser store and existing account-scoped tables/RLS. Response statistics leave a clear gap from the subject chip. The percentage and its description share one colored badge; response counts remain below it. Concurrent lookups share pending requests; successful response recording updates the cache immediately. Question navigation uses already loaded values without waiting for another request.

## Response statistics per attempt

- Collect only selected answers: instant grading records the locked answer; submit grading records final answers after submission. Unanswered questions are excluded. Lookup and failed collection never block answering or submitting.
- Same-origin Next endpoint `/api/cbt/question-stats/` validates question identifiers and revision syntax. Read requests only look up public aggregate counts for those references/revisions, without reloading source questions. Record requests fetch trusted source questions with fresh corrections and compute correctness; browser correctness/answer keys are never accepted. The revision includes effective stem, choices, images, answer and source hash, isolating statistics after corrections.
- A signed HttpOnly, SameSite guest cookie is used for both guests and logged-in browsers. Store salted visitor and attempt hashes, question reference/revision and correctness only. Next computes the attempt hash from the actual attempt ID with a separate server HMAC domain; the raw ID is not sent to the statistics database. No account/email, IP, device fingerprint, memo, raw question text or selected-answer text is stored in the statistics tables.
- Owner change (2026-10-05): repeat solving must contribute another response, without a per-browser lifetime or daily sample limit. Record one response per browser/attempt/question/revision. A new exam or `다시 풀기` has a new attempt ID and increments the aggregate again. Atomic inserts and aggregate updates still deduplicate saving retries, concurrent requests and instant/final recording of the same answer in the same attempt. Reading a question alone never creates a response; submit grading counts its final selected answer, not provisional option changes. Keep request batches bounded to 100.
- Preserve existing samples and aggregates. Old samples and old clients without an attempt ID use the reserved zero attempt hash, retaining their prior deduplication until the page is refreshed. There is no guessed attempt backfill or historical replay. Clearing cookies or using another browser can create another identity; this measures responses rather than verified unique people.
- Display actual correctness percent and `응답 N개 중 M개 오답`. At zero responses show a neutral collection state. Based on the displayed percentage: >=70% blue `많이 맞히는 문제예요`, >=50% and <70% green `대체로 잘 맞혀요`, >=40% and <50% yellow `많이 헷갈려하는 문제예요`, <40% red `많이 틀리는 문제예요`. These describe current recorded responses, not a verified measure of confusion. No historical backfill or synthetic production samples are seeded.
- The Edge backend `question-bank-stats` implements custom server-token authentication before reading/writing responses. JWT verification is off because guest requests reach it only through the Next proxy; direct calls without the private token return 401. `PASSMATE_CBT_STATS_TOKEN` is sensitive and server-only in Vercel. Supabase stores only its SHA-256 verifier in a private RLS table. The existing pinned modern-key adapter supplies the admin context; no legacy service-role key is added to Vercel.
- All three statistics tables have RLS and deny anon/authenticated reads/writes; the atomic invoker RPC is callable only by service_role. Public browsers receive only aggregate counts. The security advisor's INFO `RLS Enabled No Policy` is intentional for these server-only tables ([advisor documentation](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)). Existing unrelated policies/advisories remain untouched.
